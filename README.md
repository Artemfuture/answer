> **Задача.** Руководитель пишет системе: «Проанализируй работу отдела продаж за последние 30 дней». Источники данных — amoCRM (сделки, задачи) и телефония (записи звонков).

Здравствуйте! Спасибо за задание, было интересно. Ниже ответы по всем четырём пунктам.

### Коротко

- **Данные собираются заранее.** Синхронизация идёт каждый час и по вебхукам, звонки расшифровываются по мере поступления. На запрос руководителя система отвечает из своей базы за минуты, а не за часы.
- **Цифры считает код, LLM только объясняет.** Каждую цифру в отчёте сверяет верификатор, к каждому выводу о звонке приложена цитата с таймкодом.
- **Решения о людях и действия с клиентами остаются за человеком.** Система готовит факты и черновики.
- **Код к пункту 3 рабочий и покрыт тестами.** Тесты работают на подставных ответах API и запускаются автоматически при каждом изменении.

## 1. Архитектура

Главное, на чём я бы строил систему: не собирать данные в момент запроса. Если на фразу «проанализируй отдел продаж за 30 дней» начать выгружать всё из amoCRM и расшифровывать сотни звонков, руководитель будет ждать ответа часами. Поэтому данные из CRM и телефонии синхронизируются заранее. На запрос руководителя система отвечает уже из своей базы.

<p align="center"><img src="diagrams/architecture.png" alt="Архитектура системы" width="100%"></p>

### Агенты и источники данных

| Агент | Что делает | Откуда берёт данные |
|---|---|---|
| **Оркестратор** | LLM с вызовом инструментов. Разбирает свободный запрос: какой период, все ли воронки, весь ли отдел. Если запрос неоднозначный, уточняет у руководителя. | Сообщение руководителя |
| **CRM-агент** | Инкрементально выгружает данные по `updated_at`. Работает через OAuth и только на чтение. Запросы идут через очередь с повтором при ошибке 429, потому что лимит API — 7 запросов в секунду. | amoCRM API v4: `/leads`, `/tasks`, `/events` (смены этапов), `/leads/notes` (звонки), справочники менеджеров и воронок |
| **Агент звонков** | Расшифровывает и оценивает разговоры, привязывает их к сделкам. | API телефонии (Mango, UIS, Sipuni и т.п.): журнал звонков и записи. Там видны пропущенные звонки и разговоры, которые не попали в CRM. |
| **Аналитик** | Считает метрики кодом (SQL, pandas), а не языковой моделью. | Своя база |
| **Агент отчёта** | Пишет человеческий текст по готовым цифрам. Верификатор проверяет, что каждая цифра совпадает с рассчитанной. Если цифра «придумана», текст переписывается. | Результаты аналитика |

**Какие метрики считает аналитик:**
- конверсия по этапам и по каждому менеджеру;
- скорость первого контакта с новым лидом;
- сделки без задач и с просроченными задачами;
- пропущенные звонки, на которые не перезвонили;
- количество и средняя оценка звонков, частые возражения;
- всё то же в сравнении с предыдущими 30 днями.

**Что получает руководитель:** короткое резюме, таблицу по менеджерам, три главные проблемы со ссылками на конкретные сделки и звонки и рекомендации.

### Как обрабатываются звонки

<p align="center"><img src="diagrams/calls.png" alt="Обработка звонка" width="100%"></p>

1. **Фильтр.** Пропущенные звонки сразу идут в статистику. Разговоры короче ~20 секунд и автоответчики отсеиваются.
2. **Привязка к сделке.** Номер телефона → контакт в amoCRM → сделка, которая была открыта в момент звонка.
3. **Очередь.** Запись скачивается в S3, задача встаёт в очередь (Celery + Redis). Каждый звонок обрабатывается ровно один раз.
4. **Расшифровка.** Whisper на своём сервере или Yandex SpeechKit. Менеджер и клиент разделяются по стерео-каналам, если АТС пишет так.
5. **Оценка.** LLM проверяет разговор по чек-листу отдела продаж: приветствие, выявление потребности, работа с возражениями, договорённость о следующем шаге. Ответ — в строгом JSON, к каждому выводу прикладывается цитата с таймкодом.
6. **Сверка с CRM.** Например: в звонке договорились «созвонимся в пятницу», а задачи в amoCRM нет. Такие находки, на мой взгляд, самые полезные для руководителя.

### Где хранятся результаты

| Хранилище | Что там лежит |
|---|---|
| **PostgreSQL + pgvector** | Сделки, задачи, звонки, расшифровки, оценки, метрики и сами отчёты. pgvector нужен для поиска по смыслу разговоров («покажи звонки, где спорили о цене»). |
| **S3** (Yandex Object Storage / MinIO) | Аудиозаписи с ограниченным сроком хранения |
| **Telegram / почта / DataLens** | Отчёт для руководителя и постоянный дашборд с метриками |

**Стек:** Python · FastAPI · Celery + Redis · PostgreSQL + pgvector · Whisper / SpeechKit · YandexGPT / GigaChat · Docker

## 2. Что система делает сама, а что отдаёт человеку

| Система делает сама | Решает человек |
|---|---|
| Собирает данные и привязывает звонки к сделкам | **Выводы о людях.** Премии, штрафы, «менеджер работает плохо» решает руководитель. Система показывает факты и ссылки на них, но не выносит вердиктов сотрудникам. |
| Считает метрики и сравнивает их с прошлым периодом | **Действия в CRM и с клиентами.** Поставить задачу, сменить ответственного, написать клиенту — система готовит черновик, человек подтверждает его одним нажатием. |
| Расшифровывает и оценивает звонки | **Спорные случаи.** Плохая запись, звонок не привязался к сделке, модель не уверена в оценке, данные противоречат друг другу. |
| Находит проблемные места: сделки без задач, просрочки, пропущенные без перезвона, сделки, «зависшие» на этапе | **Критерии оценки.** Чек-лист утверждает руководитель отдела продаж. Раз в неделю он просматривает 5–10% оценок, чтобы проверить, что модель оценивает так же, как оценил бы он. |
| Готовит отчёт с рекомендациями | |

### Три главных риска

**1. Данные хуже, чем кажется.**
Если CRM ведётся формально, часть звонков идёт с личных телефонов, а переписка — в мессенджерах, отчёт будет точным ровно настолько, насколько полны данные.
→ В каждом отчёте честно показывать покрытие, например «к сделкам привязано 83% звонков». При низком покрытии система не делает выводов о конкретном менеджере.

**2. Ошибки распознавания и выдуманные выводы.**
Шум, марки и модели авто, цифры распознаются с ошибками, а LLM иногда «додумывает».
→ Цифры считает только код. Модель отвечает по жёсткой схеме. У каждого вывода есть цитата с таймкодом, которую можно открыть и послушать. Часть оценок регулярно проверяет человек.

**3. Персональные данные (152-ФЗ).**
Записи разговоров, телефоны и имена клиентов — чувствительные данные. Отправлять их как есть в зарубежные AI-сервисы нельзя.
→ Обрабатывать данные в российском облаке или на своём сервере. Маскировать телефоны и ФИО перед отправкой в LLM. Давать интеграции с CRM права только на чтение. Ограничить срок хранения записей.

> **Объём.** 10 менеджеров по 40 звонков в день за месяц — это около 9 000 звонков и сотни часов аудио. Поэтому звонки обрабатываются каждый день понемногу, а не разом по запросу.

## 3. Код: сделки без задач или с просроченными задачами

Файл: [`src/amo_problem_leads.py`](src/amo_problem_leads.py) · тесты: [`tests/`](tests/test_amo_problem_leads.py)

Вместо запроса на каждую сделку скрипт делает две массовые выгрузки:
1. все невыполненные задачи по сделкам, из них — самый ранний срок для каждой сделки;
2. все сделки.

Закрытые (этапы 142 и 143) и удалённые сделки пропускаются. У остальных проверяется, есть ли открытая задача и не просрочена ли она. Скрипт учитывает постраничную выдачу по 250 записей, пустой ответ 204 и лимит 7 запросов в секунду.

```python
"""Активные сделки amoCRM без открытых задач или с просроченными задачами (API v4)."""
import os
import time

import requests

BASE = os.environ["AMO_BASE_URL"].rstrip("/") + "/api/v4"  # https://citycar.amocrm.ru
S = requests.Session()
S.headers["Authorization"] = f"Bearer {os.environ['AMO_TOKEN']}"  # долгосрочный токен / OAuth
CLOSED = {142, 143}  # системные этапы «Успешно реализовано» и «Закрыто и не реализовано»


def fetch_all(path, params=None):
    """Постранично выгружает сущности; пустой список amoCRM отдаёт как 204 No Content."""
    page = 1
    while True:
        r = S.get(f"{BASE}/{path}", params={**(params or {}), "page": page, "limit": 250}, timeout=30)
        if r.status_code == 204:
            return
        r.raise_for_status()
        data = r.json()
        yield from data.get("_embedded", {}).get(path, [])
        if "next" not in data.get("_links", {}):
            return
        page += 1
        time.sleep(0.15)  # лимит API — 7 запросов в секунду


def problem_leads():
    now = int(time.time())
    deadlines = {}  # lead_id -> самый ранний срок среди невыполненных задач
    for t in fetch_all("tasks", {"filter[is_completed]": 0, "filter[entity_type]": "leads"}):
        deadlines[t["entity_id"]] = min(t["complete_till"], deadlines.get(t["entity_id"], t["complete_till"]))
    for lead in fetch_all("leads"):
        if lead["status_id"] in CLOSED or lead.get("is_deleted"):
            continue
        due = deadlines.get(lead["id"])
        if due is None:
            yield {**lead, "problem": "no_tasks", "overdue_days": None}
        elif due < now:
            yield {**lead, "problem": "overdue", "overdue_days": (now - due) // 86400}


if __name__ == "__main__":
    for lead in problem_leads():
        extra = f", просрочка {lead['overdue_days']} дн." if lead["overdue_days"] is not None else ""
        print(f"#{lead['id']} «{lead['name']}» отв. {lead['responsible_user_id']}: {lead['problem']}{extra}")
```

**Формат вывода** (значения условные):

```text
#1001 «Заявка с сайта» отв. 7: no_tasks
#1002 «Корпоративный клиент» отв. 8: overdue, просрочка 4 дн.
```

**Запуск:**

```bash
pip install -r requirements.txt
export AMO_BASE_URL=https://<аккаунт>.amocrm.ru AMO_TOKEN=<токен>
python src/amo_problem_leads.py
```

**Тесты** работают без сети и реального аккаунта, на подставных ответах API. Они проверяют:
- постраничную выдачу и пустую страницу 204;
- закрытые и удалённые сделки;
- сделку с одной просроченной и одной будущей задачей;
- параметры запроса;
- ошибки API 401, 429 и 500.

```bash
pip install pytest && pytest -v
```

С amoCRM в продакшене я пока не работал. Код написан по официальной документации API. Для боевого режима я бы добавил:
- автообновление OAuth-токена;
- повторы запроса при ошибках;
- фильтр по воронке и менеджеру;
- запись результата в базу вместо вывода в консоль.

## 4. Мой AI-проект

### Neuro World Bot · [github.com/Artemfuture/neuro-world-bot](https://github.com/Artemfuture/neuro-world-bot)

**Задача.** Сделать один Telegram-бот, через который можно пользоваться несколькими нейросетями, не переключаясь между сайтами и подписками.

**Что я сделал.**
- Подключил в одном интерфейсе пять AI-сервисов: три текстовые модели (OpenAI GPT, YandexGPT, GigaChat) и две модели генерации изображений (Kandinsky, YandexART).
- Добавил колоризацию чёрно-белых фотографий.
- Пользователь выбирает модель, бот запоминает его настройки.

**Стек.** Python · aiogram (async) · FSM-сценарии · PostgreSQL + SQLAlchemy · Docker Compose

**Результат.** Бот работает и стабильно ходит в пять внешних API. Главный вывод из проекта: сама модель — меньшая часть работы. Больше всего времени ушло на инженерию вокруг неё:
- у каждого сервиса свой формат запросов и ответов;
- внешние API иногда падают и возвращают ошибки, и всё это нужно валидировать и обрабатывать, чтобы бот не «ломался» у пользователя;
- секреты нужно держать отдельно от кода.

Эта задача ближе всего к вашей: собрать данные из нескольких систем, надёжно с ними работать и выдать человеку понятный результат.
